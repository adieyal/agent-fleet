# Deliver specialized displays as plugins over a generic relay

Fleet core will know how to carry and mount a specialized display but not what any display means. A plugin is a directory with a manifest (name, version, config schema), an optional host-side collector, and a browser display module. Plugins run only where the user's config enables them for a project. The collector is the only plugin code that runs on hosts: `fleet install` ships it, and `fleetd stream` runs it as a supervised subprocess (restarted with backoff, never allowed to end the stream). The collector reads its own sources and prints small JSON observations, and fleetd relays them untouched as `{"type":"plugin","plugin","version","key","data"}`. The server keeps the latest observation per host, plugin and key, and pushes it as its own SSE event; the full state document carries the current set so a reload is immediate. On the deck, core owns the screen slot in the project's room (placement, glow, hover, click) and the modal sheet. The display module is loaded with a dynamic import and implements only `thumbnail(canvas, data)`, `open(element, data)`, `update(data)` and `close()`. It never touches the three.js scene, and says so plainly when the collector's version doesn't match. Aggregation belongs in the collector, because raw sources can be far larger than a browser update: a pipeline run is about 200k events and 23 MB. The pipeline Sankey (`PipelineTracker` in fleetd, `pipelines.js` and `sankey.js` on the deck, the `pipelines` config block) becomes the first plugin and is removed from core once it runs as one. This keeps domain displays such as an invoice lab, a supplier workarea or a server room out of Fleet's source, as ADR 0004 intends, at the cost of a small public interface that must stay stable and of running user-supplied collector code on hosts, which only config-listed plugins may do.
